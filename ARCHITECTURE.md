# Architecture

## Compaction across history branches (2026-10-20)

`chat/history/branchContext.ts` selects canonical events through the current branch ancestry, applying each fork's retained revision and message anchors. Replay, durable-memory reads and compaction markers use this selection. Message rewrites record a validated `retainedThroughRevision` before removed or changed display content; the saved display transcript detects rewrites even when assistant output was not synchronized yet. Existing edit branches exclude the edited terminal user anchor when no revision boundary was recorded.

Creating a separate chat branch initializes an independent canonical document before publishing its display record. It copies the eligible ancestry through the selected cutoff, rebases completed replay state, retains matching memory snapshots and clones attachments. Completed replay state newer than the cutoff is excluded. Compaction projections append retained display output created after the snapshot, including subsequent assistant/tool output from the same turn, rather than rebuilding all raw history.

## TideUI generative interface rendering (2026-10-20)

AI-generated `tideui` blocks are a declarative, validated presentation language, not executable code. `src/lib/tideui` owns parsing, bounded syntax validation, fenced-block segmentation, incremental commitment, URL policy and limited user-initiated actions. `src/components/tideui` owns TideCode-native React presentation, charts, local controls, and sandboxed HTML previews. `AssistantMessage` uses `TideUIMessageBody` for assistant text only, retaining ordinary Markdown and persisting the original response unchanged through the existing chat transport/history. During streaming, each validated declaration line commits as it completes, including chart points, table rows, diagram items, options and tabs. Panels and child-driven widgets remain mounted as their children arrive; no native widget waits for its entire subtree to close. Malformed declarations are isolated without discarding valid siblings, and user-message actions remain inactive until completion. Finished UI blocks retain their component identity; incomplete HTML previews remain inert.

TideUI presentation is contextual: entry-like child declarations normalize in `parser.ts` to the parent's entry kind (points, events, rows, items, options or tabs). Standalone items render as text; unknown presentation names become escaped text with preserved children. `pointValue.ts` shares finite-number interpretation between validation and chart rendering; timeline point/event descriptions are textual and never enter chart-number validation. `TideUIBlock` uses the same bounded, per-declaration recovery while streaming and after completion, retaining valid siblings instead of replacing a completed interface with syntax errors. URL, action, identifier and resource validation remain enforced.

`TideUIMessageBody` retains one wrapper and the same leading Markdown key before and after the first native block. `segments.ts` detects incomplete native fence openers; normalization preserves those source tokens and the message body withholds them from Markdown until the opener is known. This prevents a transient code preview and avoids remounting preceding text at first panel insertion.

TideUI `send` buttons use the existing guarded send/queue workflow via `useChatMessageActions`, require the originating conversation to be active, and explicitly preserve unsent composer text. `draft` inserts into the composer without sending. All generated buttons are restricted to supported local UI actions; they cannot invoke the privileged TideCode tool interface directly.

TideUI rendering stability (2026-10-20): `AssistantMessage` memoizes conversation-scoped actions; the memoized message body passes only completed declaration lines to memoized UI blocks. `chatMessageContent.ts` preserves unfinished TideUI/HTML fences rather than inventing closing fences, so normalization cannot prematurely commit widgets or mount previews. Ordinary Markdown code-fence repair remains enabled. `reconcileNodes.ts` retains unchanged parsed branches across commits, and `TideUINode` supplies a memoized rendering boundary for each branch. Streaming keeps a stable inert action lookup/context, so appending declarations skips unchanged chart/control branches. Error recovery blanks invalid source lines rather than removing them, retaining source-line keys. Closed blocks and HTML previews skip unrelated prose updates. A hidden Electron regression uses the actual message list and chat CSS to check render counts, DOM/control-state retention, progressive plot geometry and retained SVG/mark identity, immediate UI/Markdown following without scroll animation, cancellation, resets, and reduced motion.

TideUI interaction extensions (2026-10-20): `src/lib/tideui/capabilities.ts` authorizes built-in actions and disables unavailable controls with visible explanations. `timer.ts` owns an absolute-deadline local timer state machine; the native timer component ticks while mounted, runs without AI-authored JavaScript, and does not claim reload persistence or OS notifications. Generated selects reuse `src/components/ui/DropdownField.tsx`; buttons/code-copy reuse `src/components/Tooltip.tsx`; chart inspection reuses `AnchoredTooltip` with SVG mark bounds. Theme-driven hover modes are allowlisted. TideUI tables use `MarkdownTable`, sharing the same GFM table components with `MarkdownRenderer` while completed rows stream and after completion. This keeps the optional HTML widget runtime independent of the code editor. Charts mount their SVG frame immediately, including when no points have arrived; the first point updates the existing plot rather than replacing a placeholder.

`useChatAutoScroll` supplies a per-content streaming revision to `useScrollFollower`. Plain chat text, Markdown tables/code, TideUI and the inner reasoning viewport share immediate following with no smooth scrolling or easing. Followed content commits pin the viewport before paint; ResizeObserver also pins asynchronous height changes before paint. Initial/reset positioning and explicit End remain immediate. The follower ignores its own programmatic scroll events and pauses on explicit upward intent; queued follow work cancels on disabling or unmount. Mutation-driven follow requests are coalesced without animating the scroll position.

`tidehtml` is the single custom HTML format, with independently optional inline CSS and JavaScript. A completed HTML block mounts immediately and runs its scripts, including after saved-message remount; incomplete fences remain inert. All HTML uses an opaque-origin iframe and restrictive CSP: inline JavaScript is permitted, while network access, external scripts, frames, workers, same-origin access and privileged APIs remain unavailable. `htmlPreviewBridge.ts` handles content-height measurement and passive wheel intent. HTML embeds transparently without a card, title, toolbar, resize handle or expansion. The iframe grows and shrinks with content without a fixed height or cap. The host validates message source, opaque origin, per-document token and numeric payloads. Wheel intent reaches the existing chat follower without cancelling wheel input or writing scrollTop, preserving native movement, momentum and chaining. Model instructions live in `electron/chat/shared/ai/prompts/chat/response.md`; the canonical grammar and examples are in `docs/tideui.md`.

HTML application actions: `TideUIMessageBody` passes the existing conversation-scoped callbacks and streaming state into `TideUIHtmlPreview`. `htmlActions.ts` validates the four permitted host operations (draft/send/copy/open), reuses the native send/draft/clipboard path, and dispatches safe HTTP(S) links. The bridge supports declarative `data-tide-action` buttons and promise-based `window.tidecode` methods in the unified HTML format. Action authorization uses a separate private credential; the bootstrap removes itself before generated scripts run. Calls require an actively dispatched trusted click, with one request per click and one pending request per page. Host checks include source, opaque origin, token, credential, monotonic request IDs and streaming restrictions. Results report acceptance or failure without remounting the iframe; stale replies cannot target a replacement frame. Source changes replace the document and execute its new inline scripts automatically. The action boundary exposes no raw tools, filesystem, history or application DOM.


HTML design reuse: `htmlTheme.ts` copies presentation tokens, and `TideUIHtmlPreview` supplies the shared TideUI stylesheet plus the inline Latin UI font. Theme and streaming-state updates cross the existing validated iframe channel without rebuilding srcdoc. A `tide-ui` custom element requests the optional runtime; `scripts/tideuiHtmlRuntimePlugin.ts` bundles the actual renderer and compiled widget styles as a lazy Vite virtual module. Plain HTML never loads this widget bundle. Each element mounts `TideUIBlock` in a shadow root, with one constructed stylesheet shared among elements. `OverlayContainerContext` keeps dropdowns and tooltips in that scope and carries the parent mobile presentation mode. `overlayViewport.ts` and the host's visible-frame bounds constrain floating UI to the visible chat region. Native widget actions use the restricted bridge, including asynchronous draft/copy/open results. The existing HTML source and per-widget parser limits apply. `.source` updates preserve renderer identity; disconnecting unmounts the tree after allowing synchronous DOM moves.

## Distribution builds

Renderer-only libraries and build tools are development dependencies: Vite bundles their runtime code and assets into `dist`, so electron-builder does not ship their original package trees. Packages imported externally by the Electron CLI/run service remain production dependencies, including `@xterm/xterm` for terminal screen modeling. Installer compression and native rebuilds retain their existing settings.

`scripts/build-cli.mjs` creates the standalone CLI with its own Node executable and a filtered `node-pty` runtime: executable JavaScript, host-platform prebuilds, compiled Release binaries, and native helper executables/libraries. Source, tests, source maps, debug symbols and other-platform prebuilds are excluded. Nonoverlapping extra-resource mappings copy CLI code and its native runtime separately: electron-builder excludes nested `node_modules` from broad resource copies, so the explicit `node-pty` mapping is required.

Icon and installer-artwork generation share `scripts/generated-assets-cache.mjs`. Fingerprints cover source assets, generator/helper code, the dependency lockfile and platform; missing or empty outputs invalidate the cache. Fingerprints are written only after generation succeeds. Caches live under ignored `build/` output and survive normal code-build cleaning. Vite skips gzip-size reporting for renderer, main and preload builds.

## Durable memory and compaction

Current implementation (updated 2026-10-20): compaction reconciles each conversation's existing `ConversationMemory` Markdown, previous continuation handoff, and evicted messages in one model call, then generates its short continuation handoff in a separate call using the updated memory. Both workers receive the same active/settled runtime meaning, bounded latest user intent, and transcript-visibility explanation through `compaction/turnContext.ts`. Their transcript covers the compacted source; recent retained messages may contain newer state. Both outputs are persisted together on the conversation's canonical `compaction_committed` event. Runtime replay injects a short instruction to read `@chat/DURABLE.md` instead of the memory contents. `tools.read` resolves that read-only alias exclusively through the current conversation ID and the latest valid memory on its active branch. Canonical history lives under the user's home `.tidecode/history/canonical-history/<conversationId>.json`, outside the project.

The continuation contains consolidated working state rather than an automatically appended prompt ledger. Historical intent remains bounded packet metadata (at most 1,000 estimated tokens, further limited by the retention target), and stored completion labels carry no authority. Runtime activity is distinct from task success; active compaction appends a continuation guard that preserves completed substeps and remaining response/work obligations. Recent history retention uses a token target and safe tool boundaries rather than a fixed message count. In-flight deduplication includes conversation ID when available, lifecycle, and the full input-message digest so different recent context cannot share a result.

`compaction/toolEvidence.ts` projects tool results for both workers before transcript serialization. For exec it extracts nested outcomes from structured metadata or the readable JSON-return/ToolResult-body format, preserving operation status, state, exit code, session, available command/subject, partial-output flags and bounded body excerpts. Each batch retains up to 100 outcomes within a 24,000-character budget; generic output uses a 2,000-character head/tail projection. This prevents large reads at the beginning of a batch from hiding later validation. Receipt extraction uses the same evidence reader and bounds carry-forward receipts to favor newer evidence. Unknown outer status remains unknown; successful API invocation does not imply process or task success. The stored history is not rewritten by this projection.

The host selects `INITIALIZE` when no previous `ConversationMemory` is supplied and `RECONCILE` when saved memory exists, including a saved empty-information placeholder. `prompts/durableMemory/index.ts` loads and separately caches `workers/durable-memory-initialize.md` and `workers/durable-memory-reconcile.md`; each API call receives only its selected complete instruction file. Initialization establishes the baseline from available evidence; reconciliation preserves applicable baseline knowledge and applies supported updates. Both return complete memory snapshots through the same model call and validation path.

The optional shared workspace `MEMORY.md` and linked detail entries remain an independent, settings-controlled feature. Per-chat durable memory is stored only in canonical chat history.

## AI execution boundary and instruction ownership

Workspace instruction application: `applyWorkspaceInstructionsContext` adds the revision-aware hidden context built by `buildWorkspaceInstructionsHiddenContext` only when root `AGENTS.md` exists as a file. This conditional context designates its applicable repository requirements, subject to higher-priority instructions and explicit user directions. It requires complete current contents, paginated reads when necessary, and rereading after compaction when the contents are missing; a receipt or summary is insufficient. It applies requirements and exceptions throughout action selection and final verification while preserving existing approval. The global mindset and stable bootstrap guidance remain unchanged. This is model guidance, not a host-enforced compliance check.

The TideCode-owned provider-facing chat tool is `exec` only. Supported provider-native tools such as `web_search` remain separate and capability-gated. `exec` executes native JavaScript in a fresh V8 isolate (`isolated-vm`) inside a disposable Node child process. `codeMode/v8` owns the execution lifecycle, worker messaging, timers and console capture. `codeMode/toolRuntime.ts` retains exact hierarchical native API paths (such as `tools.terminal.execute` and `tools.skill.load`), authorized MCP discovery, contract checks, tool concurrency and mutation ordering on the host. Only copied data crosses the tool bridge; Node globals, module loading, filesystem/network APIs and isolate reference handles are not exposed to AI code. Plan Mode's registry contains only read-only discovery, skills, `tools.plan.create`, and `tools.patch`, whose host validation allows only an update to the active plan.

Code Mode uses a 128 MB isolate memory budget and a five-minute execution deadline by default, plus input, output, concurrency and tool-call limits. The host kills the worker on cancellation/deadline and signals active tools to abort; tool cancellation remains cooperative. The app stays responsive during CPU-bound JavaScript. The isolate memory budget is enforced by V8 allocation checks, not a strict OS process-memory cap. Packaged desktop and console execution use the bundled Node binary and its matching native addon, avoiding Electron/Node ABI mixing. `isolated-vm` is a build dependency copied explicitly with its loader and platform prebuilds into the console runtime by `scripts/build-cli.mjs`; Electron rebuild must not target it. `scripts/verify-code-mode-runtime.mjs` checks that built runtime or a supplied packaged CLI directory. The run-service build identity includes the worker artifact. JavaScript state resets per exec; tool-discovery state remains chat scoped.

Each built-in API is represented in `electron/chat/shared/ai/tools/<path>/` by a TypeScript entry and adjacent Markdown usage contract. `electron/chat/shared/ai/registry/documentation.ts` loads these required documents from the configured TideCode runtime root and fails explicitly if missing. The `ai/exec` directory owns the single provider tool and its instruction contract; `ai/prompts` owns shared chat and auxiliary worker instructions. The original filesystem, terminal-session, patch and workspace security engines remain behind the API layer. User-supplied workspace `AGENTS.md` and third-party skills/MCP definitions are still external content, not bundled prompt sources.

The `exec` provider schema and description expose only a stable discovery interface, independent of mode-specific tool availability. `tools.available.list({ namespace, page })` returns deterministic pages of ten authorized names; its default root view lists connected MCP servers only, while an explicitly named namespace lists only its own tools. Unfiltered `tools.available.search` finds authorized MCP tools; specifying a native namespace searches that group. `tools.available.get({ name })` returns the authorized Markdown contract with typed arguments. Native APIs require get before execution; MCP requires list or search discovery then get. Discovery receipts persist across tool-bundle reconstructions only for the same conversation, workspace, chat mode and execution mode, in a bounded in-memory cache; the current registry and host-side permission checks remain authoritative. Mode changes are communicated through late hidden user-message contexts rather than changing the shared system prompt or `exec` tool description, improving opportunities for provider prompt-prefix cache reuse.

The renderer derives individual tool-call labels and group categories from canonical nested exec receipts. `src/components/chat/toolInvocationDiscoveryPresentation.ts` handles descriptive discovery, skill, and MCP presentation without changing provider-facing tool results.

## Theme ownership and propagation

`src/index.css` is the renderer source of truth for TideCode semantic colors. Light values are declared in the root theme and dark values override them under `:root[data-theme='dark']`. `useDocumentTheme.ts` resolves the persisted light/dark/system preference, updates the root dataset and `color-scheme`, and synchronizes browser theme metadata. `useResolvedDocumentTheme.ts` exposes the resolved theme to renderers that need an explicit mode value.

Normal React UI consumes Tailwind utilities generated from those semantic variables. `src/lib/themeColorTokens.ts` is the narrow adapter for libraries that require concrete color strings at runtime. Monaco keeps specialized editor selection/diff values but aligns its structural background, foreground, border, widget, and suggestion colors with the TideCode palette. Xterm reads the host surface plus semantic TideCode foreground/status colors while retaining a dedicated light/dark ANSI palette. Mermaid reads semantic colors before each theme-specific render, and its cache key includes the resolved theme.

Pre-render or non-React surfaces cannot depend on renderer CSS. `index.html`, `electron/window/theme.ts`, `electron/window/trayPopup.ts`, and `electron/remote/webAuth.ts` therefore mirror only the minimal palette necessary for first paint, native chrome, tray UI, and unauthenticated Remote login. Tests guard these mirrored values and core contrast relationships. The Remote login page reads the same local appearance key and system color-scheme preference before painting.

The native window-controls overlay uses a transparent background in both themes so the renderer's existing CSS titlebar paints the whole surface together. Native button symbols still use the resolved window theme; the initial window background remains opaque.

## Windows tray popup

`electron/window/trayPopup.ts` reuses the loaded custom popup with the original opacity-based toggle: opening enables mouse input, restores opacity, and raises and focuses the window; closing disables mouse input, sets opacity to zero, and stops the outside-click hook. Taking focus allows outside-click dismissal through blur even when the native hook is unavailable. The tray right-click callback owns tray toggling, while outside-click and focus-loss handlers exclude the saved tray click area to avoid reopening on the same click. That area includes the reported rectangle plus a 10-pixel margin around the opening click, covering zero-sized and incomplete overflow rectangles. Native hook positions are converted to Electron's DIP coordinates before hit testing. Pending openings are cancelled on dismissal. The existing markup and palette are unchanged.

## Embedded Browser

### Native AI browser access (2026-10-20)

The AI tool executor runs in the separate Node-based TideCode run service. It cannot access Electron webContents itself. Browser tool calls go through electron/runService/browserService.ts and the authenticated run-service socket's browser broker. The desktop main process registers itself with electron/runService/desktopBrowserHostConnection.ts and executes requests in electron/browser/agentBrowserHost.ts. The client automatically registers the host again after reconnection; requests fail explicitly when the desktop is unavailable. The run-service protocol version is bumped with this bridge. Binary screenshots are transported as bounded base64 over the private channel and decoded into existing AI image results in the run-service executor. Browser UI IPC handlers for annotations and Developer Mode are registered eagerly by pageActions.ts, independently of whether any browser tab has been attached.

The desktop browser and Agent Mode share Electron's built-in Chromium engine. The `native_browser` discovery namespace contains open, read, tabs, interact, terminate, and devtools without renaming the `tools.browser.*` callable paths. `electron/browser/agentTabs.ts` requests real browser tabs from the workspace renderer, waits for its normal `<webview>` to attach, then registers that same guest as the AI's browser target. No separate hidden AI browser window, duplicate page, or external Chrome installation is used. `agentCdpSession.ts` coordinates the persistent per-tab CDP connection, bounded diagnostics, and native DevTools exclusivity. `agentPageCapture.ts`, `agentPageStructure.ts`, `agentPageInput.ts`, `agentPageDiagnostics.ts`, and `agentAnnotations.ts` handle screenshots, accessibility/DOM-backed element references, guarded input, permissioned diagnostics, and annotation validation respectively.

The conversation/project-scoped annotation store is electron/history/browserAnnotations.ts. The desktop preload and browser page-action IPC own its renderer bridge. Runtime appends annotation context to the last user model message (without mutating persisted user text); browser.read can return visual, structure, combined, or annotation views. Combined screenshot results reuse the existing image-result presentation alongside literal text output. Full Developer Mode is session-scoped, project-specific, user-enabled from the browser toolbar, and checked in the native diagnostics layer; the AI cannot grant itself permission. Only normal browser sessions are eligible. See docs/browser-agent.md.

`BrowserPanel.tsx` owns tab sessions, address drafts, navigation state, and the Electron webview elements. The application window attaches guest behavior and manages floating DevTools windows. Guest setup runs without synthetic user activation, including when Electron defers script execution until loading stops.

New tabs render the local `BrowserNewTabPage.tsx` with an empty address. No webview or iframe is started until a nonempty address or search is submitted. URL normalization keeps Google as the search provider, independently of the home view. Home resets the tab to a fresh local new-tab state and releases its page session.

`browserHistory.ts` normalizes completed website visits into at most six distinct HTTP/HTTPS origins and validates saved PNG icons. `useBrowserHistory.ts` owns their React state and local-storage persistence per project, migrating existing URL-only records when read. Credentials and page paths or queries are not saved.

`electron/browser/faviconCache.ts` tracks favicon URLs reported by native page WebContents. It downloads bounded images over HTTP/HTTPS with no credentials, limits and validates redirects, and deduplicates requests (including failures) in a bounded cache. The native preload favicon bridge accepts only a guest ID owned by the requesting application window, not an arbitrary URL. Results are associated with the current page and discarded after navigation or destruction. The history hook decodes these local data URLs into 32×32 PNGs; recent-site shortcuts render the persisted bytes without any network request.

Closing the last tab calls the Browser panel's parent close action. `BrowserWorkspacePanel.tsx` removes that project's initialized Browser session, unmounting its guests, and `ChatInterfaceContent.tsx` closes the panel. The renderer retains at most two recently active project Browser sessions so inactive guest WebContents cannot accumulate without bound; locally saved recent sites remain intact for every project. Reopening an evicted or explicitly closed Browser creates a fresh new tab.

The embedded Browser is desktop Electron-only. Remote web clients do not render the Browser control, do not expose a Browser RPC namespace, and do not create virtual BrowserWindows or screencast page frames on the host.

DevTools are initialized on explicit user opening, rather than during guest load. The renderer requests floating DevTools through the preload bridge; the main process owns the child windows. Page title, favicon, and loading updates retain the existing webview session.

## Chat attachments and workspace aliases

Chat file, folder, and image attachments are copied into TideCode-managed per-draft or per-conversation storage under the history area instead of being added to the active workspace. The main process owns attachment persistence, draft adoption, conversation cloning, listing, and cleanup. Folder copies reject symbolic links and apply TideCode workspace ignores plus nested `.gitignore` rules.

Remote browser attachments use an authenticated same-origin HTTP upload path owned by the desktop remote host. Browser files are streamed to the laptop and committed into the same managed attachment storage and `@attachments/...` alias space used by desktop attachments. Remote folder uploads preserve their browser-exposed relative paths, while incomplete upload sessions are cleaned up by the host.

Desktop and remote chat share immediate optimistic user-turn presentation. Final message IDs are allocated before persistence; existing chats show the local turn and fresh drafts use a temporary transcript scoped to their unique draft attachment ID until creation completes. Saving reconciles onto the same IDs, and provider execution still waits for checkpoint/context/history persistence. Composer revisions and draft identity prevent asynchronous settlement from clearing or restoring over newer text/attachments; selection checks prevent a pending send from stealing another chat. Failed presentation rollback applies to the latest queued runtime messages and removes only its own pending turn. Edited turns retain their existing identity and branch behavior. Remote history/shared-run events remain authoritative.

Send admission, pending draft status, pre-stream cancellation and stop-operation deduplication are scoped to an individual draft or saved conversation. `useChatSendActions` tracks the draft-to-conversation association for the lifetime of each send, so stopping a newly saved chat reaches its originating workflow. A stop in an empty draft never searches other running chats. Revert pins cancellation to its target conversation and waits for that run to settle before rolling back the pending turn. Multiple chats in the same project may run concurrently; they still share the project's workspace files and existing mutation/checkpoint controls.

Assistant turn actions can branch a conversation from a completed assistant message. Branch creation is handled by the history store through `createConversation`: the new conversation stays in the source folder/project, clones the source conversation's managed attachments, copies transcript messages through the selected assistant message, preserves the source title and chat mode, and synchronizes the copied transcript into canonical chat history before selecting the new conversation.

The renderer refers to persisted attachments through stable `@attachments/...` aliases and workspace files through `@workspace/...` aliases. Workspace tool path resolution maps those aliases, enabled `@skills/...` paths, and temporary read-only `@tool-output/...` paths to their authorized backing locations while retaining the existing sandbox/full-access checks for absolute paths. Large generic tool results are capped at 2,000 lines or 50 KiB for model context; the complete output is retained under the home-scoped TideCode tool-output store for seven days and exposed back to the agent only through `@tool-output/...`, which normal `read`, `grep`, `glob`, and `list` can inspect in Sandbox Mode. Terminal model output is tail-biased under the same limits and switches to the same saved-output path once the command output crosses that threshold, while user-facing terminal display output remains separate. `@tool-output/...` is never a valid mutation target or terminal working directory. Terminal working directories for other authorized aliases use the same alias resolution, with the resolved virtual root added only to that command's sandbox roots. Conversation identity is part of tool context so `@attachments/...` always resolves within the current chat.

Text reads respect a bounded byte budget, paginate by line offset, and use an opaque continuation cursor for exceptionally long individual lines, including lines in saved `@tool-output/...` files. Image read results are passed to the model through ephemeral visual-result messages instead of embedding large image content in the regular text output; those transient messages are stripped from persisted chat history.

Windows workspace copy/cut writes native file-drop clipboard data in addition to TideCode's internal marker, allowing Explorer and other native applications to receive the selected files while TideCode can still recognize its own clipboard operations.

## Renderer resource lifecycle

Full Git text snapshots are demand-driven: Diff and active workspace editors can request contents, while Source Control rows and closed surfaces use status metadata with native Git line statistics. `electron/git/diffStats.ts` parses NUL-delimited numstat and keeps bounded streaming line counts for untracked/unborn files, so the visible badge does not require full file bodies. Git snapshots also carry separate staged (HEAD-to-index) and unstaged (index-to-worktree) line counts in both metadata and full modes. A bounded set of repository-wide numstat reads supplies these counts, skipping scopes without matching changes and reusing combined counts for unstaged files when the index has no staged changes; no per-file Git statistics process is launched. Renderer scope projection uses the native counts before and after preview hydration, and status equality/reconciliation includes scope-only count changes. Untracked files use their streamed added-line counts; conflicted previews retain their existing HEAD-to-worktree counting semantics. Settings suspends full-content demand without discarding editor state. Snapshot reads serialize per workspace/request kind with one replaceable pending invalidation; mutation callers wait for a fresh read. Full-content cache retention has a three-entry/16 MiB estimated string budget and releases on final hook-consumer cleanup; generation checks prevent closed requests from refilling it. Active snapshots remain usable outside the inactive cache budget. Startup relies on selected-workspace hooks instead of prefetching every saved project's Git state.

Individual collapsed tool results retain their header/data but do not parse Markdown or mount Monaco result bodies. Expanded views use existing loading/size estimates; collapse unmounts the view and existing unreferenced-model expiry still applies. Browser live-session preservation is unchanged. The historical findings and approved implementation scope are in `docs/resource-audit-2026-10-17.md` and `docs/plans/electron-resource-optimization.md`; measurements and limits are recorded in `docs/performance.md`.

Source Control reads a single Git porcelain status snapshot to preserve staged, unstaged, rename, and unmerged metadata and surfaces errors rather than replacing failed reads with empty lists. Full Git file snapshots carry HEAD, Git index, and working-tree text separately; the existing Staged and Unstaged views project HEAD-to-index and index-to-worktree diffs. Status-only snapshots retain metadata without pretending to contain renderable file contents. Diff opening falls back to cached status rows while full snapshots hydrate; cold content demand also starts an independent status read. Expanded metadata rows use the existing loading view without mounting Monaco. Panel-open reads coalesce with active reads, while mutation invalidations retain a pending fresh read. Workspace editor tabs filter metadata-only rows out of text baselines; metadata alone cannot mark a tracked tab as newly created. Quick and advanced commits use the shared renderer confirmation when nothing is staged, and its explicit `includeUnstaged` authorization is carried through the controller before Git stages all changes. A successful local commit followed by failed push/PR follow-up is returned with a warning rather than reported as a failed commit. History refresh compares actual refs and commit rows, not just HEAD, so remote-only updates remain visible.

Heavy editor and preview runtimes are demand-loaded. Monaco and its language workers are not prewarmed during application startup, Settings plus its MCP/skills state mount only while Settings is open, and PDF/DOCX renderer modules load only when those preview types are requested. Shiki highlighting is also initialized on first use rather than at renderer bootstrap.

Long-lived renderer caches use bounded retention. Highlighted code tokens, Mermaid SVGs, compaction markers, full Git diff snapshots, and Monaco diff models all have explicit caps; unreferenced Monaco diff models also expire after a short grace period. Native source-control notifications remain the primary refresh path while slower polling acts only as a fallback.

Compaction markers load for the conversation being opened and refresh after its compaction events. Startup does not prefetch markers for the full sidebar: extracting them reads and parses canonical history, so an all-conversation prefetch would overlap full-history allocations. The marker cache coalesces ordinary requests for the same conversation and retains up to 128 conversation marker lists.

Idle reconciliation is event-first. Context usage refreshes on message, stream, focus, compaction, and workspace events, with a one-minute visible-window fallback instead of continuous ten-second estimation. Git source-control notifications remain primary, with a short diff fallback because nested Windows worktree edits are not guaranteed to reach the non-recursive watcher. Status-only Git snapshots can populate file lists while previews await full file contents; missing bodies never become renderable empty diffs. Main-process gitignore, skills discovery, and conversation checkpoint caches are bounded so changing projects and traversing large workspaces cannot grow process memory indefinitely.

The shared run-service is demand-started. Read-only startup reconciliation probes for an already-running service so the desktop UI can attach to CLI or remote work, but a quiet desktop launch does not spawn the detached run-service process until a chat run, terminal, compaction, shared-runtime update, or another run-service mutation requires it.

Chat runtime retention protects the selected conversation and every sending or shared running conversation. It retains at most three other recent transcripts within a 16 MiB estimated string budget; evicted conversations reload from persisted history when selected. Context estimation uses one active request and one replaceable pending refresh across hook effect changes, so file watcher and compaction events cannot overlap full transcript estimates. Its estimator builds provider-visible tool schemas without constructing a `CodeModeExecutor`, caches schema token counts per provider, and runs independent workspace, model image-support, and canonical-history lookups concurrently.

PDF previews own reference-counted document leases. Active previews pin their document; unreferenced workers expire after one second and are also bounded by three documents and a 32 MiB source-string budget. Clearing the cache retires active documents until their owners release them. Pages render only within 400 pixels of the viewport, cap their canvas at four million pixels, cancel render tasks during cleanup, and release offscreen canvas storage. There is no second bitmap cache.

Chat and Monaco share a single lazy Shiki runtime. Monaco registers asynchronous token provider factories and loads each grammar when its language is first needed. Main-process TypeScript snapshots retain at most six requests and 32 MiB of source strings; the renderer retains four requests and 16 MiB. Monaco project libraries release 30 seconds after their final editor consumer closes, allowing quick tab switches to reuse declarations.

History traversal reads two conversation files at a time and transforms each into a summary before advancing. Completed shared runs retain their reconnect projection for 60 seconds, then release projections, follow-ups, sequence entries, and timers. Conversation runtime and settled compaction metadata have 128-entry limits with active work protected. Service connection probes coalesce, and failed handshakes destroy sockets and release receive buffers. Terminal retention removes unreferenced exited sessions after five minutes, including their legacy owner state, and bounds completed command metadata at 64 records per session or five minutes. Active operations and attached exited terminal output remain available. Closing Browser DevTools destroys its floating child window.

`scripts/profile-memory.mjs` measures the built application or Vite renderer with a temporary home, Chromium profile, synthetic history, isolated service namespace, and separate remote port. It records process working sets/private bytes and renderer heap/canvas metrics without forcing garbage collection. Findings and reproduction commands are in `docs/performance.md`.

## Remote project folder selection

Desktop project creation keeps the native Electron directory picker. Remote web clients use an in-app folder picker backed by the desktop host: the renderer requests host roots, directory listings, and folder mutations through the existing `tidecodeHistory` remote bridge, then passes the selected absolute path through the existing project creation flow. Rename, delete, copy/cut, and paste actions execute on the desktop host, while the web client receives directory metadata rather than file contents.

Diff file headers share `DiffFileHeader.tsx` across lightweight collapsed rows and expanded `DiffViewer` previews. Conversation rows opt into a 52 CSS-pixel header with a reserved separator and a 72 CSS-pixel action slot; other diff callers retain their default header sizing. Collapsed conversation rows have an explicit 53 CSS-pixel total height, shared with virtual-list offsets, so fractional border rendering under display scaling cannot accumulate spacing errors. The virtual list measures expanded rows in a layout effect and observes later preview resizes; collapsed rows always use the exact collapsed height, never a cached expanded height. No hidden editor measurement was restored.

## Explicit chat mention references

The desktop/remote composer catalogs File, Folder, Attachments, Skills, and MCP. `chatMentions.ts` serializes selected references as `[[tools.read:path]]`, `[[tools.list:path]]`, `[[tools.skill.load:name]]`, or `[[tools.available.search:server-name]]`, retaining exact workspace/attachment aliases inside file and folder markers. The UI keeps compact labels and persisted mention maps. Attachment retention and image previews resolve the target inside the marker. Existing saved history is not rewritten. CLI file, folder, and skill completions emit the same tool prefixes.

MCP mentions request server-specific discovery through `tools.available.search` with namespace `mcp`; contract retrieval and host permissions remain authoritative.

## Terminal identity and recovery

Workspace terminal tabs retain the broker session ID returned at creation and send it with input, resize, and close requests. Numeric IDs remain part of PTY transport and event indexing; broker identity validates events and asynchronous failures before they update a tab, preventing a reused numeric ID from targeting a replacement session.

`terminalSessionLifecycle.ts` owns the shared asynchronous creation/replacement boundary. Each attempt uses a generation-specific creation key. Lost-session and service-disconnection input failures recover without replaying uncertain input; stale creation results release only their own session. Setup and service failures leave an error state from which Restart can retry. The broker distinguishes missing references from unknown numeric IDs, permits closing dead records, and keeps retained output readable after session loss.

## Browser menu and page actions

`DropdownPopover.tsx` shares portal positioning and outside-click/Escape dismissal between `DropdownField`, `BrowserMenu`, and `BrowserNewTabMenu`. The tab bar retains new-tab and fullscreen buttons beside the browser menu; a single overlapping divider paints above the tab viewport to preserve its edge. The active tab exposes page actions through `useBrowserPageActions.ts`. Zoom choices are available from navigation start, including pending redirects, and are applied when the guest becomes available. New tabs do not show zoom controls. Request revisions prevent late zoom responses from replacing newer choices.

`electron/browser/pageActions.ts` validates workspace-window and guest ownership for zoom and screenshots and restricts cookie/cache clearing to the active owned browser partition. This does not clear TideCode's default session. Page DevTools use a floating child BrowserWindow only; the dock modes, native docking menu, reserved page area, and dock bounds/visibility IPC have been removed.

`BrowserScreenshotButton.tsx` starts capture from each tab's URL row; `BrowserScreenshotToast.tsx` owns saved-file actions and timed feedback through a portal into the positioned tab container, anchored below the URL row within browser bounds. Toast surfaces and controls use semantic theme tokens. Screenshot availability uses document readiness, separate from zoom readiness: main-frame navigation disables capture until dom-ready; same-document navigation preserves it. The active tab passes its project root through `useBrowserPageActions.ts`. `electron/browser/screenshots.ts` creates `.tidecode/browser-screenshots/`, rejects redirected screenshot folders, and writes uniquely named PNGs without overwriting. Main-process screenshot actions validate the workspace sender and restrict clipboard/reveal operations to existing browser screenshot files in that folder. ## Incognito browser sessions

The new-tab dropdown offers normal and incognito tabs. Normal guests use `persist:tidecode-browser`. `electron/browser/sessions.ts` creates a unique nonpersistent partition per workspace-window/project private session, with HTTP caching disabled. Native tab tokens retain the session even for empty incognito tabs. Closing one private tab preserves the session for its siblings; closing the last token revokes access, waits for attached guests to be destroyed, then clears storage, cache, and connections. Renderer reload/crash and owner destruction revoke private sessions as well.

`BrowserTab` carries its mode and partition. `BrowserPanel.tsx` releases private tab tokens on close/unmount, skips private visit/favicon history writes, and passes no recent-site shortcuts to private new tabs. Only normal guests enter the shared favicon cache. Private tabs show an incognito indicator and cannot save screenshots, enforced in both the renderer and native capture handler. Menu cookie/cache clearing validates the active partition against its window owner, including on empty tabs. Floating DevTools and page zoom continue to target the owned guest.

Edited-send presentation suppresses the history-cutoff scroll anchor while an optimistic edited message is visible. The existing explicit follow-latest signal can therefore anchor the submitted edit at the bottom without the edit/revert anchor pausing following again.
