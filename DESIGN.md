# Design

## User-facing errors (2026-10-20)

Application errors use the browser screenshot notification's neutral raised surface, subtle border, compact typography, shadow, dismiss button, and action styling. Transient action failures use the global, timed, hover/focus-pausing notification host; persistent file, settings, and connection problems remain visible in their own panels using the same shared surface. Do not use competing red error banners or expose raw exception messages, stack traces, local paths, or numeric engine codes as primary error copy. Preserve validation next to its field and preserve destructive confirmation styling. Developer-facing tool/terminal diagnostics and generated-content errors remain available separately or behind a disclosure.

## Branch and revert continuity (2026-10-20)

Branching keeps visible messages through the selected assistant response plus the canonical context and durable memory valid at that point. Reverting between compactions 2 and 3 resumes from compaction 2 with the retained suffix. Every new fork records its canonical revision boundary so later reverts cannot restore discarded snapshots. Display history remains available; model context uses the retained compacted window. A new chat owns its memory independently of its source. Branch failures include the underlying error in the chat error message.

Splitting reasoning/tools from final response text must preserve the saved response identity on the actionable final text. Branching copies the complete original message, including its reasoning/tool history, rather than its shortened presentation fragment.

## Sidebar project selector (2026-10-20)

Project rows keep the title above the path or description, with hover highlighting following the pointer and the ellipsis action's neutral button hover kept separate from the row. The project dropdown shows no checkmarks. Choosing a project immediately filters history to that project and keeps the filter selected while its new conversation is created. Chats belongs in the history filter, not the project dropdown. The reasoning-effort dropdown prefers opening below and flips only when viewport space requires it.

## TideUI component language and visual system (2026-10-20)

Choose the response presentation according to its usefulness. Native TideUI is preferred for structured comparisons, meaningful options, timelines, metrics, progress and useful interactions, without waiting for an explicit request for visuals. Use Markdown for explanations, code, commands and short answers; combine formats without duplicating information. Use custom HTML when its layout or local interaction capabilities improve the response beyond native components. Keep interfaces proportional, controls functional, follow-up actions clear and displayed data supported by evidence. Respect an explicitly requested response format.

HTML embeds visually into chat without an outer card, border, title, toolbar, manual resize handle or Expand control. Height follows actual rendered content, including subsequent growth and shrinkage, with no fixed height or cap. Wheel scrolling over HTML uses native browser movement, momentum and scroll chaining. The bridge only relays intent so upward scrolling pauses following; it never cancels wheel input or manually applies wheel movement. One `tidehtml` format accepts HTML with optional CSS and/or JavaScript. Completed blocks render and run automatically, including on saved-message remount. Running JavaScript state survives surrounding chat streaming. Preview document defaults have zero outer margin, transparent backgrounds, adaptive text colors and a thin scrollbar; authored styles can override the presentation. Sandboxed iframe isolation is retained.

Custom HTML can request Draft, Send, Copy and safe-link Open through the restricted action bridge after response completion. Genuine clicked controls initiate these actions; page-load code and synthetic clicks cannot. Action controls keep their labels unchanged and add no routine progress or success text. Declarative HTML controls retain their page state, disable while pending, display errors only, and disable Send after acceptance. Interactive JavaScript receives `{ok,error?}` results to drive its own UI. Send uses the existing visible-message workflow without consuming unsent composer text; Draft intentionally fills the composer.

Custom HTML can freely mix its own design with the shared TideUI CSS classes and actual native widgets embedded using `tide-ui`. Shared design tokens follow the active app theme. Native widgets retain their usual controls and state; shadow-scoped styles keep custom CSS separate from widget presentation. Dropdowns and tooltips stay scoped and fit the visible chat area, including when the iframe document is taller than chat. Native widget use is optional and does not introduce another response format or execution control.

TideUI is a distinct TideCode-native visual language: AI models describe content and local interactions using two-space indentation and short component declarations. React components supply all layout, controls, sizing and appearance. Use semantic colors from `src/index.css` through the scoped `tideui.css` sheet, not OpenUI or generated inline CSS. Dashboards, metrics, charts, diagrams, tables, forms and action buttons must stay readable in dark/light modes and narrow chat widths. Code blocks expose Copy automatically. User-triggered `send` buttons submit a visible user turn, whereas `draft` only fills the composer. Custom HTML remains isolated from native controls and does not inherit privileged application capabilities. See `docs/tideui.md` for the supported grammar.

TideUI interaction follow-up (2026-10-20): Generated selects and tooltips must reuse TideCode's shared `DropdownField` and `Tooltip`/ `AnchoredTooltip` components rather than inventing parallel dropdown or tooltip designs. Dashboard cards and metrics can request `highlight`, `lift`, or `glow` hover/focus states using semantic palette tokens. Chart marks support hover/focus inspection and optional selection with accessible data labels. Native focus timers display truthful local lifecycle state and explicit non-persistence limits. Avoid stream-time animations and repeated viewport jumps; respect reduced motion.

Streaming adds completed declarations while retaining existing component instances and local input/expanded state. Incomplete tokens and unrelated trailing prose do not rerender committed UI; appending a sibling skips unchanged presentation branches. Finishing a valid response enables its guarded actions without remounting its controls. Autoscroll follows plain text, Markdown tables/code, TideUI and reasoning text immediately before paint, without smooth scrolling, easing, or animated catch-up. Initial positioning and explicit return-to-latest stay immediate, and upward user intent pauses following. Rendering stability comes from retaining committed components and holding back incomplete declaration lines. Panels fill progressively; charts add completed points and tables add completed rows without waiting for the whole widget. Chart frames retain their geometry and SVG identity as points arrive.

Entry wording is tolerant and contextual: timelines accept textual event-like entries, lists/comparisons accept entry-like children, and standalone items display as text. Charts keep real numeric validation. Unknown presentation names degrade to escaped text, while invalid declarations cannot erase the remaining completed UI. The first native panel retains the preceding Markdown DOM and layout wrapper; partial native opening fences never flash a code preview. Submitting an edited message returns to the bottom and resumes following; the history-cutoff anchor is suppressed for the optimistic submitted bubble.

## File editing

Keep the authoritative-workspace-instructions designation in the conditional hidden user context supplied when root `AGENTS.md` exists as a file. The concise injection requires reading the file fully and following every applicable requirement and exception rather than treating it as optional reference data. Changed revisions receive a reread reminder. Missing files and directories named `AGENTS.md` receive no injection. Leave the system prompt and global mindset unchanged.

Discovery refinement (2026-10-19): both native and MCP tools use consistent one-line descriptions and namespace selection. `available.list` pages namespaces or tools; `available.search` ranks names and descriptions within an optional namespace with a ten-result maximum. Invalid search parameters produce an explicit error rather than silent correction.

Current discovery behavior (2026-10-19): `tools.available.list()` starts at a namespace index, not the native-tool page. Selecting `native` or an MCP server namespace lists that namespace's tools in pages of ten with short descriptions. MCP tools do not require an extra `mcp` namespace selection. Search remains names-only, and get returns full contracts.

Prefer `tools.edit` for exact replacements and `replace_all: true` when every occurrence should change. A missing match or ambiguous non-global match rejects the whole operation before writes. Multiple replacements are applied in order, across files, with the same visible diff presentation as `tools.patch`. Keep patch for complex contextual edits and write for whole-file creation.

## Per-chat durable memory

Implemented storage choice (2026-10-18): keep durable Markdown in the conversation's canonical compaction history, not in a separate project DURABLE.md file. Chats in the same project have independent durable state. Successful compaction saves both the reconciled long-term memory and a separate short-term continuation summary; reopening injects a short instruction to read the current chat's memory using `tools.read({ path: '@chat/DURABLE.md' })`. Optional shared workspace MEMORY.md remains a distinct existing feature, controlled separately in Settings.

Conversation continuity (2026-10-20): durable memory preserves relevant facts, constraints, decisions, architecture and consequential open work across repeated compactions. The short handoff preserves the immediate objective, supported progress, validation limits and next action. Both consolidate by subject instead of accumulating numbered prompts. Evidence must distinguish plans, attempts, changes and verification; repeated summaries do not increase certainty, and active/settled runtime status does not establish task success. Compaction during an active turn preserves finished substeps and the remaining work or final response. Each worker receives the previous handoff and explicit visibility/lifecycle context so unseen recent progress is not invented. This supports continued use of the same chat without treating bounded memory as a verbatim archive.

The host explicitly selects first-memory creation (`INITIALIZE`) or existing-memory reconciliation (`RECONCILE`). Creation extracts the initial supported knowledge; reconciliation retains applicable older facts and uncertainty while applying targeted corrections and additions. Each scenario has a separate complete Markdown instruction file, including its applicable reliability rules and output requirements. A call receives only the selected scenario's instructions. Both operations produce a complete memory snapshot.

Compaction preserves scoped nested tool outcomes before shortening bulky logs. A batch of source reads followed by validation must retain the later command outcomes and useful search results for both workers. Tool-call success, running/completed state, process exit code and partial output remain distinct. Bounded evidence and newer receipt priority reduce stale open work caused by lost results; they do not mechanically determine whether a user's full goal is complete or rewrite existing saved summaries.

## AI tool invocation presentation

Chat displays a TideCode `exec` call through its individual nested API invocations, preserving file diffs, terminal sessions, plan previews and errors. The model may also receive provider-native search tools. The fixed `exec` description lists discovery APIs only: `tools.available.list` pages native names by default, MCP server namespaces when selecting `mcp`, and tool names within a selected server namespace; `tools.available.search` finds native/MCP capabilities globally or within a namespace; and `tools.available.get` retrieves Markdown contracts. The UI labels these as Listed tools, Searched tools, and individual Retrieved contract blocks. Mode transitions in hidden user-message context tell the model to refresh the available catalog; inaccessible tools remain blocked by host permissions without mode-specific changes to the shared system prompt or `exec` definition.

The model sees a concise native API name catalog in `exec`. Search returns names only; `tools.available.get` supplies instructions, argument schema, and exact signature when needed. For connected MCP capabilities, the model searches first, then gets the matching full contract. A tool's first execution requires its contract to have been retrieved; subsequent executions in the same chat can reuse the discovery state. Unauthorized or removed capabilities are never enabled by cached discovery.

Tool rows present discovery search/get, skill operations, and nested MCP calls using descriptive state-dependent titles and their query/name target. Discovery and skill results reuse the established expandable result body, with structured JSON formatted for readability only. Group summaries distinguish searches, retrieved contracts, skill operations and MCP executions from terminal and file work.

Internal discovery operations emit UI-visible nested receipts even when no external tool executes. Contract retrieval uses the shared label `Retrieved tools` rather than an individual tool name, so multi-contract exec programs no longer fall back to `Ran code`.

When a model attempts an authorized API without retrieving its contract first, the host tool bridge fetches and records the exact `available.get` contract, stops that exec program before the attempted operation, and returns the contract with retry guidance to the model. The renderer shows only the successful `Retrieved tools` entry. MCP capabilities still require discovery by search first; mode and workspace authorization are unchanged.

Code Mode accepts native JavaScript rather than a custom language subset. Standard functions, classes, collections, Promises, callbacks and error handling follow V8 semantics. Programs use top-level await/return, copied JSON-compatible tool inputs/results, bounded timers and captured console output. Machine access stays behind registered `tools.*` calls. Each execution has a fresh isolate and a disposable worker; cancellation and resource failures end that execution without blocking TideCode's UI.

Source transport instructions require literal multiline file contents, replacements, patches and documents in outer `exec.payloads`, referenced from the executable program. The main exec guidance, payload schema description, shared source-quality guidance and mutation contracts reinforce this rule so embedded backticks and interpolation expressions remain destination-file data. Computed content remains supported. A wrapper parse error directs the model to move the raw text into a payload before retrying.

## Light and dark color system

Source Control retains the existing Commit split button, Staged/Unstaged sections, file rows, history graph, and accent palette. File status indicators use the established Git semantic colors; conflicted paths are identified explicitly. Destructive discard actions require user confirmation. When no changes are staged, quick and advanced commits use the same TideCode-styled confirmation dialog before staging all current changes; operation notices distinguish complete success, partial success (local commit followed by failed remote action), and errors without clearing an unsuccessful commit message.

Advanced commit opens as a modal over the existing Source Control panel without closing it. Its remote-only choices remain disabled when no remote is configured; completing a local commit without finishing a remote push/PR step is clearly labeled as partial success. The composer branch selector keeps its popup open after a failed checkout so the Git error is visible, and closes after successful checkout. Creation and checkout preserve local changes on failure; no auto-pull is triggered by a branch switch.

TideCode uses one semantic color hierarchy for all app-owned UI. Light mode starts from a light canvas and distinguishes controls and nested surfaces with progressively darker muted, hover, and pressed surfaces. Dark mode mirrors that relationship from the existing near-black canvas: panels, fields, raised menus, hover states, and pressed states become progressively lighter so controls remain visibly separated instead of blending into the black base.

`src/index.css` owns the renderer palette. Components should use semantic roles such as `background`, `surface`, `surface-muted`, `surface-raised`, `surface-hover`, `foreground`, `muted-foreground`, `border`, `action`, `brand-soft`, and the success/warning/danger/info families rather than local light/dark color pairs. Primary actions use `action` with `action-foreground`; soft brand selections use `brand-soft` with `brand-soft-foreground`. Git additions, removals, modifications, and renames use their semantic Git roles consistently across chat, Explorer, commits, and Source Control.

Settings follows the same hierarchy even when a page owns its controls directly rather than using a shared component. Dialog backdrops use the shared overlay role, fields use muted surfaces, popup/raised content uses raised surfaces, and selected navigation/cards use the shared brand-soft treatment. Semantic status colors remain distinct from selected-state colors.

Primary actions and checked switches use the same soft green selected surface as active conversation-history and Settings navigation items, not the neutral sidebar background: `#d9e9e6` in light mode and `#223630` in dark mode. Primary action text and checked switch thumbs use dark green (`#315f59`) in light mode and white (`#ffffff`) in dark mode; selected history-item labels retain the softer brand-soft foreground. Hover surfaces follow `accent-hover`, and light-mode primary controls use the same subtle active-item border as selections. Unchecked switches remain neutral and distinct.

Only light mode draws an accent outline around soft-green selected items and actions. In dark mode, the active-item border and brand border resolve to transparent so the green surface itself defines the selected state without a visible rim. This applies to conversation history, Settings navigation, primary buttons, checked switches, active account cards/badges, and selected options. Preserve layout-sized transparent borders and ordinary structural, input, focus, and error borders. The Source Control Commit split action retains exactly one divider between its actions in both themes, even though its outer outline blends away in dark mode.

Literal colors remain appropriate where the color is part of the content or another established visual language: user images, PDF/DOCX paper, actual websites, file-type icons, syntax highlighting, terminal ANSI colors, Git graph lane colors, and third-party brand marks. These exceptions must still remain readable against both TideCode themes.

## Browser interaction

Native browser-agent UX (2026-10-20): Keep TideCode's original Electron browser rather than launching Chrome. The six AI browser tools are discovered through `native_browser` but retain their existing `tools.browser.*` paths. AI-created tabs appear directly in the native browser tab strip with a small AI icon and use the exact same Electron webview as the user, without mirrored pages. `browser.read` defaults to a true 1280x720 image with concise DOM/accessibility targets, and click/fill prefer fresh element references while preserving coordinates for canvases. Browser tool disclosures show content-sized screenshot previews and literal text rather than rendered Markdown. The URL row has an annotation picker and an explicit Full Developer Mode toggle; annotations are attached to the active conversation and received by the AI with the next user turn. Incognito guests are excluded. Failed, stale, hidden, or obscured elements must not trigger guessed clicks.

Browser opens as a resizable right sidebar. Browser, Diff, Source Control, and Explorer replace one another in that side-panel area. Browser and Diff can expand across the workspace and return to their sidebar width. Browser's new-tab, fullscreen, and three-dot menu controls and Diff's fullscreen action use the terminal's 28-pixel icon-button treatment. Browser's action row stays vertically centered and its new-tab action uses the shared Tooltip. The + button opens the shared-style dropdown with New tab and New incognito tab; keyboard arrows, Enter, Escape, and outside dismissal follow the existing dropdown behavior. A single divider before the new-tab control overlaps an adjacent tab's border and paints above clipped tabs, keeping a visible edge without double dividers.

The terminal header always reserves and shows its restart action. It is disabled while the active session connects or when no tab is selected, so the neighboring actions do not shift between terminal states. A lost session reconnects without replaying the keystroke or command whose delivery is uncertain. Restart replaces the session with a fresh shell; if setup fails, the tab shows the error and remains restartable. Late output, exit notifications, and input errors from a previous session must not affect its replacement or another tab.

Desktop panel resizing stops before the chat composer loses its 512-pixel panel minimum. Visible editor and side-panel widths participate in the available-space budget; dragging and releasing handles must preserve control alignment and avoid layout jumps. Desktop Browser, Diff, Source Control, and Explorer share one width and common resize bounds; mobile Explorer retains its own width. Remote/mobile chat retains its responsive width behavior.

Browser startup, new tabs, and Home show a local TideCode page with a search/URL field. The address starts empty and receives focus when the new tab becomes active. Searches from either field use Google; URLs open directly. Empty submissions do nothing. The idle view has no loading indicator or page DevTools, and Reload is disabled until navigation. Home starts a fresh page session and resets navigation history.

The text-only `tidecode-word.svg` serves as a large new-tab heading, using the theme-aware brand color without the symbol or a square background. It scales down to fit narrow panels and sits close above the search field. The group sits above the panel's vertical midpoint, with twice as much remaining space below as above. The center search field is compact, uses a neutral “Search” hint, rounder corners, and no focus outline or changing border. Enter submits the field; there is no arrow button. Search-provider branding and explanatory hints are omitted. Up to six recently visited websites appear below it, most recent first, saved locally per project. Shortcuts show the website's favicon captured during browsing, cached locally across restarts; missing or failed icons use the site's initial. Opening a new tab never performs favicon lookups. Existing visits acquire icons when revisited. Shortcuts open the site's home origin rather than a previously visited private path or query.

Closing the last Browser tab closes the Browser panel and returns to chat, without closing TideCode. It does not create a replacement tab. Reopening Browser starts a fresh new tab while preserving recently visited websites.

Browser page state is preserved for the two most recently active projects. Opening Browser in a third project evicts the least-recent inactive project session and releases its guest pages; that project's saved recent websites remain available when Browser is opened again.

Users can edit the address while the current page loads. Background load completion and metadata updates must preserve their text and keyboard focus. Page setup does not simulate user interaction, and address editing does not use repeated focus restoration or remove the page from keyboard navigation.

Clicking the webpage transfers focus normally. Fullscreen is a standalone tab-toolbar button. The camera is labeled Screenshot, sits on the right of the URL row, stays disabled before the page document is ready, enables on dom-ready without waiting for full resource loading, and automatically saves the visible webpage viewport as a PNG in the user home `~/.tidecode/browser-screenshots/` folder. Filenames use `browser-screenshot-<sanitized-hostname>-<base36-timestamp>-<8-random-hex>.png`. A Screenshot saved toast overlays the top-right of the browser below its URL row, stays within the browser during resizing/fullscreen, and uses theme surface, text, and action colors in light and dark modes. It has no success icon, uses compact spacing, and wraps its actions within the browser width. It offers Copy path, Reveal in File Explorer, and Copy image. Only the running action button is disabled; other actions keep their appearance and remain usable. Copy buttons temporarily show Copied path/Copied image for two seconds on independent timers without changing width; revealing adds no success message. It dismisses after three cumulative idle seconds; hovering, keyboard focus, and pending actions pause the remaining countdown without restarting it. Pointer focus alone does not hold the toast open after the mouse leaves. Action errors stay visible. The camera is disabled on new tabs or without a project; save failures appear beside the camera. The three-dot Browser menu offers text-only Open DevTools, page zoom, Clear cookies, and Clear cache. It has no profile label. Open DevTools and zoom are hidden on a new tab; navigating to a website immediately exposes usable minus/plus/reset controls, even during redirects and before full loading completes. Choices made before Electron exposes the guest are applied as soon as it becomes ready. Reset returns to 100%, with steps bounded from 25% to 500%. Cookie and cache clearing apply to the active tab's Browser session and report completion or failure in the menu.

DevTools open only as a floating window, from the menu or existing keyboard shortcuts. Repeated Open DevTools actions focus the existing floating window. Closing it releases the window; opening again creates a fresh inspector. Browser content always uses the available page area, with no right/bottom docking controls or reserved dock space.

The Browser control is available only in the desktop Electron app. Remote web clients do not show or open the Browser surface, and there is no remote page virtualization or screencast interaction path.

## Resource retention and previews

Desktop and remote Send show the accepted user message before checkpoint/context/history saving finishes, preserving its identity when saving completes. Required persistence still precedes provider execution. Saving or failure handling must not overwrite newly typed composer text or another conversation's draft.

Each new draft has independent send, saving and stop state, including drafts in the same project. Opening a new chat while another response is running or saving permits a separate submission. Stop and Revert affect their originating chat; completing or rolling back an older send must not select it over a newer draft or clear the newer draft's message. Reverting an unresponded turn preserves its conversation record while removing the pending turn from saved history.

Closed Diff/Source Control surfaces keep lightweight Git metadata without full-content refreshes unless an active workspace editor needs a Git baseline. Collapsed individual tool results show headers/counts without invisible editor premeasurement; opening uses the existing loading/size presentation. Browser toolbar toggling continues to preserve live pages, and closing the final tab releases that project's session. No Browser session/state policy changed as part of this optimization.

The selected chat and ongoing background runs stay available. Three recent inactive transcripts may be reused within a memory budget; other chats reload from saved history when selected. Retention never deletes conversations or their attachments.

Compaction markers load with the opened conversation. Starting on an empty draft does not load markers for saved chats; switching chats loads that chat's markers, and completed compactions refresh the visible markers.

Switching models or providers preserves the conversation's compacted context and completed turns since compaction, including when switching back to a previously used model. It does not restore discarded history or rewind to that model's older context. Token usage can vary with provider formatting and overhead; changing the model must not undo compaction.

PDF previews preserve page positions, page count, scrolling, panning, and zoom while rendering pages near the viewport. Offscreen pages keep their layout and recreate their canvas when approached. Very large pages or high zoom levels use a capped raster resolution while retaining their displayed dimensions.

## Chat mentions

Chat mentions keep compact labels in the composer and rendered messages while resolving to their canonical paths on hover. Path-backed image attachments show only an image preview on hover. Non-image mentions remain path-only. Image previews use the attachment data already held by the chat model rather than reading from the workspace or hard-coding filename extensions.

## Chat attachments

Attaching a file, folder, or image inserts a compact mention directly into the composer instead of adding a separate attachment-pill row. Attachment mentions participate in normal mention editing, queued-message editing, and message history. Image mentions show their preview on hover with even padding around the preview.

The attachment picker and drag/drop flow accept workspace items and external files without placing copies into the user's workspace. Stored attachments remain scoped to the draft or conversation, and removing the corresponding mention removes the attachment from the message state. Folder attachments omit ignored workspace content and symbolic links.

Remote browser paste, file selection, and drag/drop persist arbitrary browser files through the desktop host instead of limiting attachments to browser-readable text and images. PDFs and other binary files therefore behave like desktop file attachments. Browser-exposed directory drops or clipboard entries are uploaded as one folder attachment with their nested relative paths. When the browser does not expose pasted folder contents, the composer reports that limitation explicitly instead of labeling the folder as an unsupported file type.

## Remote project folder picker

The sidebar Add Folder action keeps the native operating-system folder dialog on desktop. In remote web, it opens a TideCode-rendered Explorer-style dialog for the desktop host filesystem. The dialog provides quick locations and drives, breadcrumb navigation, back/forward/up controls, directory search, explicit refresh, and context-menu folder actions using the same visual treatment as the workspace explorer. Folder context actions include new folder, paste, delete, rename, cut, copy, copy path, and copy relative path; the main workspace explorer context menu also exposes Refresh. Quick-access navigation avoids reloading when the requested location is already open. The bottom Folder field shows only the selected folder name, remains editable, and offers typo-tolerant suggestions from the current directory only. Windows system folders are suppressed while ordinary user-hidden folders remain visible. Narrow remote viewports use the same picker full-screen rather than opening a second mobile-specific implementation.

## Windows tray menu

The TideCode notification-area menu retains its custom colors, sizing, layout, and labels. Closing retains the original Git sequence: disable mouse input before setting opacity to zero rather than hiding or destroying the native window. The preloaded popup takes focus when opened so clicking elsewhere can dismiss it through focus loss without depending solely on the global mouse hook. One right-click opens the popup; a second right-click closes it and returns without reopening. Only the tray callback toggles on an icon click. Outside-click and focus-loss handlers ignore the icon's effective hit area, which includes the opening click plus a 10-pixel margin even when Windows reports an empty or incomplete tray rectangle. Other outside clicks, right-clicks inside the popup, Escape, and either menu action close the popup. Left-clicking the icon closes it and shows the main window.

Diff retains its cached changed-file list on opening/reopening while refreshing contents. A cold project obtains its status list independently of full file text. Expanded pending previews retain their header, file actions and expansion state with the existing loading presentation; Staged/Unstaged per-file +/− counts appear with the cached rows from scope-specific metadata, including while previews are pending. Hydrating preview contents does not replace them with a different counting method. Switching projects never presents the previous project's list. Closed-panel full-content release remains enabled.

Conversation Diff file names, icons, counts and action controls use the same header geometry before and after expanding a file, while its preview loads and after collapse/reopening. Counts retain their width beside truncated long names; the action column reserves the same space for Staged and Unstaged rows. The clicked header does not change its baseline or spacing to make room for a preview. Rows below an expanded preview still move normally as content is revealed or its measured height changes.

## Mention catalog

The @mention catalog contains File, Folder, and Skills, with Attachments shown only when the current chat has attachments and MCP shown only when an enabled MCP server is connected. Category availability updates from current draft attachments and live MCP state without refreshing the chat. Attachment and MCP results remain usable while workspace files are indexing. Rendering and keyboard selection use the same visible category order. The composer displays short `@name` labels; sent messages carry bracketed exact tool references. Files and image attachments request `tools.read`, folders and folder attachments request `tools.list`, skills request `tools.skill.load`, and MCP server names request `tools.available.search`. Workspace/attachment aliases remain intact inside path markers.

MCP suggestions include only enabled, connected servers and show their description or the neutral label "MCP server", without connection-status text. MCP icons and mention highlights use theme-aware violet tokens. Choosing a server does not itself execute a tool. The model searches that server's MCP tools, retrieves the relevant contracts, and reports unavailable servers rather than substituting another.


Incognito tabs use an in-memory session shared only by private tabs in the same project/window, separate from normal cookies and login state. They have an incognito indicator in the tab and address field, show no recent-site shortcuts, and do not add visits or favicons to normal history. The private session is discarded after its last tab closes or its renderer is replaced. Screenshot saving is disabled in incognito so it does not create project files. The new-incognito action is unavailable in the web runtime, where Electron session isolation is unavailable.
