## How to use memory in future work

Before a substantial implementation:

1. Read the memory index.
2. Open only the entries related to the requested subsystem.
3. Verify load-bearing facts against the current source, tests, and Git state.
4. Treat memory as durable context, not authority. Current code and the latest user request win when they disagree.
5. After a change, update an existing entry if a durable fact changed or became clearer.
6. Create a new entry only when no existing topic can hold the knowledge without becoming confusing.

## Update rules

Update memory when:

- the user confirms a durable product or workflow decision;
- a non-obvious architecture or compatibility constraint is discovered;
- a bug’s root cause/workaround will matter to future changes;
- a persisted schema, migration, path, or event contract changes;
- a security boundary or verification requirement is established;
- a meaningful feature changes how the system should be reasoned about.

Do not update memory for routine progress, temporary branch state, ordinary source facts, speculative conclusions, credentials, private data, or hidden chain-of-thought.

## Quality requirements for entries

Each entry should be self-contained and useful in a new session. Include exact paths, symbols, commands, contracts, invariants, rationale, verification date, and uncertainty where relevant. Prefer precise revision over duplicate entries. Keep Markdown human-readable and avoid copying large source files into memory.

If an entry becomes stale, correct it in place and preserve still-valid material. If a fact is disproven and no longer has future value, remove it rather than leaving contradictory historical notes.
