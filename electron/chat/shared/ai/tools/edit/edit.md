# tools.edit

## Keep edited source readable

Write source for people to read and maintain. Keep block bodies and nested structures in expanded multiline form with consistent indentation. Put distinct declarations, statements, and sibling structural elements on separate physical source lines, including every embedded language. Editor word wrapping does not count. Concise replies and simple implementations do not justify compressed source. Preserve the surrounding project's readable conventions; do not minify unless explicitly requested or preserving an existing generated/minified artifact.

Before submitting replacements, inspect their formatting. After editing, read back the affected source, following continuation output when truncated, and correct any packed sections introduced by the edit before finishing. Successful replacement, valid syntax, and a working preview do not verify source readability. If the user reports compressed source, fix and inspect the authorized source rather than only acknowledging the mistake or offering to format it later.

Through exec: `{"code":"return await tools.edit({ changes: [{ path: 'src/example.ts', oldText: payloads.beforeText, newText: payloads.afterText }] });","payloads":{"beforeText":"const offset = 6\n","afterText":"const offset = 8\n"}}`. Obtain the tool contract first. Exec recovers misplaced top-level strings, exact bare payload bindings, and unique case/underscore/hyphen name variations; conflicting values and ambiguous aliases reject. This recovery does not loosen source matching.

Preferred for text replacements in existing files. Supply `changes: [{ path, oldText, newText, replace_all?, line?, before?, after? }]`. Changes apply sequentially in array order; later changes may intentionally match earlier replacements. Match exact text first, then recover a unique indentation-only mismatch when exact matching fails. Specify a 1-based starting `line`, exact preceding `before`, or following `after` context to select a unique duplicate occurrence. Without disambiguation, duplicates reject with candidate line numbers; `replace_all: true` replaces all matching candidates. LF/CRLF/CR matching is normalized; original file formatting is preserved. All changes are validated before any writes and committed atomically with rollback on recoverable failures. After rejection, reread the affected range and rebuild conflicting replacements instead of resubmitting unchanged batches. For complex contextual hunks use `tools.patch`; for new files use `tools.write`. Put literal multiline matching and replacement text in outer `exec.payloads`, then reference those payloads in `oldText`, `newText`, `before`, or `after`. Preserve the source's backticks and interpolation expressions as data instead of nesting raw source in executable template strings.

Use `line` only when you have verified the exact 1-based starting line of `oldText` from the current file. It is an exact constraint, not a hint to search nearby; do not estimate it. Account for earlier changes in the same batch that shift the target. When the line number is uncertain, omit `line` and use enough exact surrounding text in `oldText`, or exact `before`/`after` context, to identify the intended occurrence uniquely.
